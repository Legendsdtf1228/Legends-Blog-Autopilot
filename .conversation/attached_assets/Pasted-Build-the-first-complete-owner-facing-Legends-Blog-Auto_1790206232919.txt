## Goal

The backend foundations already exist. Do not rebuild them.

Connect the accepted research, ReaderTask, clustering, knowledge, evidence, title, and brief components into a coherent owner-facing application that Logan can open, understand, and operate without developer knowledge.

The immediate deliverable is a polished, functional Replit preview of the owner console. Production publishing must remain paused.

## Product experience

The interface should feel like a finished business application for Legends DTF Prints—not a developer dashboard, database browser, or generic admin template.

Use a clean black, charcoal, white, and restrained gold visual system matching the Legends brand.

Prioritize:

- clarity;
- large readable status labels;
- plain-language explanations;
- obvious primary actions;
- responsive desktop and mobile layouts;
- minimal clutter;
- no unexplained technical terminology.

Use the existing application stack and component conventions. Do not replace the framework or rewrite the project.

## Primary navigation

Build a persistent application shell with:

1. Dashboard
2. Content Pipeline
3. Research
4. Knowledge
5. Questions for Logan
6. Publishing Calendar
7. Settings
8. Activity and Errors

## 1. Dashboard

Create an owner summary showing:

- current operating mode;
- system status;
- production paused/running state;
- next scheduled action;
- articles by pipeline stage;
- topics ready to advance;
- topics blocked by missing evidence;
- questions waiting for Logan;
- knowledge awaiting approval;
- recent publishing activity;
- errors requiring attention;
- rollout progress;
- Shopify connection status.

The top of the dashboard must answer:

- Is the system running?
- Is anything wrong?
- Does Logan need to do anything?
- What will happen next?

Include a clear pause control, but do not allow the UI preview to enable production publishing.

## 2. Content Pipeline

Build a visual workflow with these stages:

- Researching
- Needs Evidence
- Needs Logan
- Ready
- Writing
- Quality Review
- Scheduled
- Published
- Blocked

Each content item should show:

- proposed title;
- canonical ReaderTask;
- intended reader;
- decision the article helps make;
- evidence readiness;
- current status;
- next action;
- scheduled date when applicable;
- reason if blocked.

Support filtering by status, content category, audience, and date.

Do not create fake production records. Use clearly labeled development fixtures only when the local database contains no records.

## 3. Article Detail

Create a detail screen containing:

- title;
- reader question;
- question provenance;
- audience;
- situation;
- problem;
- decision or action;
- desired outcome;
- constraints;
- proposed outline;
- evidence budget;
- approved supporting facts;
- unsupported or prohibited claims;
- contradictions;
- quality status;
- publishing status;
- activity history.

Actions must be gated by the item’s real state.

Do not provide an override that bypasses evidence, approval, freshness, authority, scope, contradiction, or AUTO eligibility rules.

## 4. Research

Expose the existing ReaderTask and clustering system in owner-friendly language.

Show:

- active ReaderTasks;
- canonical task for each cluster;
- supporting demand evidence;
- merge confidence;
- review candidates;
- hard conflicts;
- cluster evidence readiness;
- last evaluation time.

Technical trace information may appear in a collapsible “Why?” panel.

## 5. Knowledge

Build a knowledge center for:

- Legends products and services;
- policies;
- pricing and cost facts;
- turnaround information;
- firsthand experience;
- DTF technical information;
- UV DTF information;
- embroidery information;
- local business facts;
- authoritative general education.

Each entry must clearly show:

- approval state;
- source type;
- applicable scope;
- freshness;
- effective dates;
- public-use permission;
- contradictions;
- revision history;
- claims it supports.

Approval controls must continue to bind approval to the immutable revision/content hash.

Changing content must create a pending revision rather than silently modifying an approved fact.

## 6. Questions for Logan

Create a focused inbox containing only merchant questions that require Logan’s input.

Each question should explain:

- what information is missing;
- why the system needs it;
- which articles or ReaderTasks it affects;
- required date, units, product, process, or geographic scope;
- whether the answer may be used publicly.

The answer workflow must:

1. collect the answer;
2. collect applicable scope and effective date;
3. ask for public-usage permission;
4. show the exact fact to be approved;
5. save it as pending;
6. require explicit approval before it supports an article;
7. re-evaluate every affected cluster after approval.

Do not ask questions already answered by current approved knowledge.

## 7. Publishing Calendar

Build a weekly and monthly calendar showing:

- planned topics;
- writing status;
- scheduled Shopify publication;
- blocked items;
- empty publishing slots;
- completed publications.

Production remains paused. The calendar may display and manage development schedules but must not publish to Shopify during this milestone.

## 8. Settings

Create understandable settings for:

- operating mode;
- content frequency;
- preferred publishing days;
- topic categories;
- local versus national emphasis;
- content tone;
- default article depth;
- Shopify blog destination;
- notification preferences;
- emergency pause.

Display the future operating modes:

- Paused
- Draft Only
- Approval Required
- Guarded Autopilot
- Full Autopilot

Only Paused and Draft Only may be selectable during this milestone. The other modes must be visibly locked with an explanation of what must be completed before they unlock.

Never weaken existing rollout requirements.

## 9. Activity and Errors

Show:

- evaluations;
- status transitions;
- approvals;
- invalidations;
- retries;
- publishing attempts;
- integration errors;
- blocked claims;
- user actions.

Each entry should explain what happened and whether Logan needs to act.

Do not expose secrets, tokens, connection strings, personal customer data, or raw stack traces in the normal owner view.

## Safety boundaries

Do not change:

- evidence approval rules;
- immutable content hashes;
- freshness requirements;
- technical source authority;
- process or geographic scope requirements;
- contradiction blocking;
- SourceEvidence allowlists;
- clustering thresholds;
- AUTO_ELIGIBLE thresholds;
- opportunity decision policy;
- existing reservations;
- legacy opportunity rows;
- rollout counting;
- publishing defaults.

Do not connect to production credentials or production data.

Use a disposable local PostgreSQL database.

Production must remain:

- disabled;
- paused;
- `draft_only`;
- unable to auto-publish.

Do not begin automatic article publishing in this milestone.
